# 模型卡：流失预测（Churn Scoring）

> 按 [Model Cards](https://arxiv.org/abs/1810.03993) 的思路记录：模型做什么、用什么数据、
> 效果如何、不能用来做什么。

---

## 1. 模型概览

| 项 | 内容 |
|---|---|
| 任务 | 二分类：预测用户在下个观测窗口内是否流失（`Churn = 1`） |
| 用途 | **排序**——把用户按流失概率排队，决定客服/电销先联系谁 |
| 不用于 | ① 直接拒贷/降额等惩罚性决策；② 替代归因分析；③ 跨行业/跨运营商直接套用 |
| 实现 | `src/ml_churn.py`（scikit-learn Pipeline，含预处理） |
| 版本 | 数据集：Telco Churn 7,043 × 21；代码：`v1.0.0` 之后的 `feat(ml)` 提交 |
| 复现 | `python src/ml_churn.py --data data/telco.csv --out results/ml` |

## 2. 训练数据

| 项 | 内容 |
|---|---|
| 来源 | 公开数据集 Telco Customer Churn（IBM Sample Data Sets） |
| 规模 | 7,043 行 × 21 列，1 行 1 用户 |
| 标签分布 | 正例 1,869（**26.54%**），负例 5,174 |
| 时间维度 | 无。数据是单一快照，没有"哪一天观测、哪一天流失"的时间戳 |
| 缺失 | `TotalCharges` 11 条空白（在网 0 个月的新客），按 `月租 × 在网月数` 回填 |
| 切分 | 分层留出 20% 做测试，训练集内 5 折分层交叉验证（`random_state=42`） |

## 3. 特征

原始 19 列（去掉 `customerID` 与标签）+ 4 个派生：

| 派生特征 | 计算 | 业务含义 |
|---|---|---|
| `service_count` | 6 个增值服务中为 `Yes` 的个数 | 服务越多、切换成本越高 |
| `avg_monthly` | `TotalCharges / max(tenure, 1)` | 历史平均客单价 |
| `is_new` | `tenure <= 6` | 对应报告里的"留存悬崖" |
| `charge_ratio` | `MonthlyCharges / avg_monthly` | 识别"最近被涨价"的用户 |

预处理：数值列中位数填补 + 标准化；类别列 `OneHotEncoder(handle_unknown="ignore", min_frequency=20)`。

## 4. 效果（真实数据，7,043 行）

| 模型 | ROC-AUC | PR-AUC | 阈值 | Precision | Recall | 预期净收益（测试集） |
|---|---|---|---|---|---|---|
| LogisticRegression | **0.846** | 0.654 | 0.16 | 0.376 | 0.976 | **9.47 万元** |
| RandomForest | 0.841 | **0.655** | 0.10 | 0.348 | 0.976 | 9.31 万元 |
| HistGradientBoosting | 0.825 | 0.612 | 0.05 | 0.386 | 0.936 | 9.13 万元 |

- 交叉验证与留出集差距 < 0.01，**没有明显过拟合**
- 三个模型差距很小 → **不建议为了 0.001 的 AUC 换更复杂的模型**；可解释性优先时选 LR
- 特征重要性 Top5：`Contract`、`tenure`、`InternetService`、`TotalCharges`、`is_new`
  —— 与 SQL 归因的结论一致（合同、在网时长、网络类型）

## 5. 阈值与业务口径

阈值不是 0.5，而是按净收益扫描得到：

```
净收益 = TP × (ARPU × 12 × 挽回率 − 单次成本) − FP × 单次成本
       = TP × (74.44 × 12 × 0.35 − 20) − FP × 20
```

| 参数 | 取值 | 依据 |
|---|---|---|
| ARPU | 74.44 元/月 | 报告 Q11：流失用户平均月租 |
| 挽回率 | 35% | 保守假设，需 A/B 实验校准（见 `experiments/abtest_design.md`） |
| 单次成本 | 20 元 | 权益 + 人力 |
| 观测窗口 | 12 个月 | 保守取一年 |

> ⚠️ 这三个参数是**假设值**，不是实测。上线前必须用真实实验数据替换。

## 6. 已知局限

1. **无时间维度**：无法做真正的"未来流失"预测，只能做横截面打分
2. **样本偏差**：公开数据集来自单一运营商、单一时点，不能直接外推到其他市场
3. **成本参数未校准**：挽回率 35%、成本 20 元都是假设
4. **不含因果**：模型说"这类人容易走"，不等于"联系他就能留住"
5. **标签泄漏风险**：`TotalCharges` 与 `tenure` 高度相关，若业务中该字段延迟更新，线上效果会衰减

## 7. 公平性与合规

- 数据集含 `gender`、`SeniorCitizen`、`Partner` 等敏感属性，当前**作为特征纳入**
- 若用于真实业务，建议做两件事：① 移除 `gender` 后重训并对比 AUC（差异 < 0.01 则移除）；
  ② 禁止基于敏感属性做差异化定价或差别服务
- 模型输出仅用于**排序和人工复核**，不应自动执行任何惩罚性动作

## 8. 监控建议

| 指标 | 频率 | 触发动作 |
|---|---|---|
| 特征分布漂移（PSI > 0.2） | 每周 | 检查数据管道 |
| 预测正例率突变（±20%） | 每周 | 检查上游数据或阈值 |
| 上线后 AUC（需延迟标签） | 每月 | 低于 0.80 触发重训 |
| 阈值对应的触达人数 | 每周 | 与客服人力对齐 |
